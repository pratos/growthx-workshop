Release behind a flag

cp-10 · 2026-10-28 · final · pratos with Claude Code · 2 min read · built from docs/plans/stages/cp-10-release.plan.json

decide() already refuses Resolve without the resolve-thread flag, but the screen still offers it. This stage makes the screen ask the same Flags service, then ships to production through docs/RELEASE.md's three questions: is it right, can you watch it, can you undo it.

Where we are

cp-09 runs seven browser tests green. resolve-thread is seeded off, on for admin and pratos, and checked in decide(). Sam still sees Resolve, types a decision, and meets a refusal. Production has no accounts until you add one.

  • Flags.enabledFor in apps/api/src/services.ts is what Commands.dispatch hands decide(); the new route calls the same function, so they cannot disagree.
  • A percentage is a stable bucket per participant and flag (bucket()), so pct 5 keeps the same people on.
  • just flag user appends to the allowlist; just flag off also clears the allowlist and percentage.
  • /healthz returns version.id, the id just rollback api <id> needs.
  • .github/pull_request_template.md asks the three release questions on every PR, so the plan fills them in.

Where we end up

On production, Resolve appears for you after flag user and a tab switch, with no deploy, and disappears after flag off. Sam reads why it is missing. The PR answers the three questions.

Not doing

Out of scope for this plan, each with the reason in the same line.

  • A flags page for people who are not admins.
  • Pushing flag changes to open tabs; the page rechecks on focus.
  • Removing the flag after full rollout; that is a later release.
  • A new migration; 0001 and 0002 only add tables.

Approach

The screen first, so the flag decides what people see. Then docs/RELEASE.md's three questions, in order, each a phase.

Decisions

Each real choice in this plan, with the options compared side by side. A decided one is locked on its choice; open “Compare the options” to see why.
