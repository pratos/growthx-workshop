The plan document: comments that end in decisions, live

cp-05 · 2026-10-28 · final · pratos with Claude Code · 4 min read · built from docs/plans/stages/cp-05-plan-document.plan.json

A Plan gets its document: Participants open a Thread on a Block and resolve it into a Decision that stays attached to that Block. Every tab on the Plan sees each change at once, through the PlanRoom's hibernating sockets. Resolving ships behind resolve-thread, checked in decide().

Where we are

cp-04 has accounts and sign-in, the Flags service with resolve-thread seeded off but allowlisted for admin and pratos, admin pages and Playwright. There is no Plan yet. No Durable Object, thread commands, event log per Plan or page at /plans/:id.

  • The PlanRoom appends a command's events in one synchronous block, so ThreadResolved and DecisionRecorded land together or not at all.
  • Flags cross into the Durable Object as a list of names; a function would arrive as an RPC stub whose promise reads as true.
  • Thread commands carry by in the body (CommandEnvelope); the page's acting as field sets it, starting as pratos.
  • docs/DOMAIN-VOCABULARY.md has no ThreadClosed and bans verdict, so the vocabulary check catches the first pass by name alone.
  • The upcaster is a pure function tested on a verbatim v1 stream; PlanRoom.read() does not call it yet.

Where we end up

Two tabs on /plans/gh-12: a Thread opened in one appears in the other, and resolving it shows who decided what. A first pass that calls the event ThreadClosed fails just domain-vocabulary-check, and just review main flags it.

Not doing

Out of scope for this plan, each with the reason in the same line.

  • Hiding Resolve without the flag; until the release stage the page shows the refusal.
  • Reopening a Thread or editing a Decision; a change of mind is a new Thread.
  • Sessions and the agent; they arrive at cp-06.
  • Wiring the upcaster into read(); this stage proves the rung on a recorded stream.
  • Checking a thread command's by against the sign-in; sessions do that from cp-06.

Approach

Domain first, because event shapes are the contract the room, page and tests read. Then the room and its API behind the flag, then the live page, then the checks that catch a wrong name.

Decisions

Each real choice in this plan, with the options compared side by side. A decided one is locked on its choice; open “Compare the options” to see why.

One record or two when a comment is resolved?

Chosen: Two records · pratos · 2026-10-28

Two records keep "the Thread is resolved" apart from "this was decided", so the decision log counts Decisions on its own. Both options were built and their tests passed.

Design language

The look this plan’s screens use: tokens first, then each component rendered live in every state it can be in.

The plan page is a working surface, read often and quickly. Tailwind greys on the theme background until cp-07 restyles it; black for the action, emerald only for live and decided, amber for a refusal.

not started · 0/3

  • apps/api/src/plan-room.ts
    One object per Plan: an events table in its SQLite, synchronous appends, every socket told. Socket pings are answered by the runtime (setWebSocketAutoResponse), so keep-alives never wake the room.

    Flag off, a guest is refused; pratos records both events; a bad envelope is typed.
