Vocabulary, architecture and event design

cp-02 · 2026-10-28 · final · pratos with Claude Code · 3 min read · built from docs/plans/stages/cp-02-design.plan.json

Before any engine code, the product gets its words, its map and its event design. This stage names every noun once, as an entry and as a schema, draws the Chopin-like plan room, and settles where the agent's work runs, so every later agent says the same things.

Where we are

cp-01 deploys both Workers from main with a version label and a rollback; migrations run by hand. There are no domain words yet: no schema package, no vocabulary, and an architecture doc that covers only two Workers and D1.

  • The check reads every Not: line in docs/DOMAIN-VOCABULARY.md and scans exported names and command or event fields under packages/schema and packages/domain.
  • A banned word used only as a plain Schema.Struct key passes the check today; as an export, or inside defineEvent fields, it fails.
  • bun scripts/arch.ts --coverage blocks packages/schema until "Where it lives" names it, so the map changes with the package.
  • A sign-in is never called a session: in this product, a Session is where Participants ask the agent.

Where we end up

just domain-vocabulary-check passes, and fails when a banned word such as Verdict is exported. The architecture map and the agent-loop decision report open in the browser and show the plan room design.

Not doing

Out of scope for this plan, each with the reason in the same line.

  • The engine or any decider; cp-03 builds the engine, later stages the Thread and Session.
  • Routes or pages; the API and the web app stay as cp-01 left them.
  • Renaming Session to Thread for the agent; that waits until after the workshop.
  • Workspace words such as repo, branch or preview; nothing uses them yet.

Approach

Words first, because every later name comes from them. Then the map, which places those words. Then the event design, and the one decision it depends on.

Decisions
