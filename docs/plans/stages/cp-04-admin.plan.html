Admin workflows and the first end-to-end test

cp-04 · 2026-10-28 · final · pratos with Claude Code · 4 min read · built from docs/plans/stages/cp-04-admin.plan.json

An admin can now see and steer the running product: a dashboard, every account, the event log with secrets masked, and the flags that switch behaviour on. Every page is an API call first, behind one admin check. The first Playwright test proves it in a real browser.

Where we are

cp-03 ended with the engine (packages/engine), sign-up, sign-in and sign-out on it, and three seeded accounts: Admin, Sam and the agent. Accounts carry an admin bit, but nothing reads it yet, there are no flags, and no test drives a browser.

  • AccountOpened records a passwordHash and SignedIn a tokenHash; the event log shows both unless the API masks every key matching hash, password or token.
  • A form submitted before React hydrates posts natively, so a test that types too early sees a reload. Tests wait for <html data-hydrated>.
  • stream_events, accounts and sign_ins are already in D1 from 0002_accounts.sql, so the dashboard counts with plain SQL and needs no new projection.
  • currentAccount in apps/api/src/auth.ts already returns the admin bit, so requireAdmin is one more check on the same sign-in.
  • Under just up the API is reached only over the service binding, so pages and Playwright test it; nothing curls it yet.

Where we end up

Signed in as Admin, /admin shows counts, accounts, the event log with passwordHash="•••", and flags you can switch. Sam is refused with the reason. just e2e admin passes in Chromium against the migrated, seeded app.

Not doing

Out of scope for this plan, each with the reason in the same line.

  • Writing accounts from the dashboard; just user-add opens them.
  • Reading flags in decide(); the first flagged command, ResolveThread, arrives at cp-05.
  • The screen asking which flags are on for someone; that waits for the release stage.
  • Recording flag changes as events; a change overwrites the D1 row.

Approach

API first, because the page and any agent with an admin sign-in must do the same things. Then the pages over it, then the browser test that walks every refusal and the admin path.

Decisions

Each real choice in this plan, with the options compared side by side. A decided one is locked on its choice; open “Compare the options” to see why.

Is every admin action an API first?

Chosen: Yes: the page only calls the API · pratos · 2026-10-28

The web Worker has no data access by rule, and an agent signed in as an admin must be able to do what the page does. One requireAdmin gate covers both.

Design language

The look this plan’s screens use: tokens first, then each component rendered live in every state it can be in.

Admin is a working surface: an admin glances at numbers and scans rows now and then. Tailwind greys on the theme background as the pages ship them; black for the action, amber for a refusal, emerald for a flag that is on.

Phase 1 API: flags and admin reads, admins only

not started · 0/4

/flags, PUT /flags/:name and /admin/* answer 401 without a sign-in, 403 for Sam, and data for Admin; secrets print as •••.

Changes

Each file this phase touches and what must be true of it afterwards. Code appears only as a contract other code depends on.

  • apps/api/migrations/0001_flags_and_projections.sql
    Create the flags table, default off; the file also holds the empty decisions projection.
  • apps/api/src/services.ts
    Add Flags: on when enabled, allowlisted, or the participant's stable bucket is under percent.
  • apps/api/src/auth.ts
    Add requireAdmin: 401 without a sign-in, 403 naming the account that is not an admin.
  • apps/api/src/flags-admin.ts
    FlagsAdmin over D1 or a Map; a bad name or percent is FlagInvalid, 400.
  • apps/api/src/admin.ts
    Summary counts, accounts with live sign-ins, newest events with hash, password and token masked. POST /admin/accounts: an admin opens an account (name, email, starting password, role) through Accounts.open, recorded as AccountOpened; 400 on bad input, 409 when taken.
  • apps/api/src/index.ts
    Mount /flags and /admin; both sub-apps run requireAdmin on every route.
  • apps/api/test/flags-admin.test.ts
    Set then list, an invalid percent, an empty name: all on the Map layer.
  • packages/db/seed.ts
    Seed resolve-thread off, allowlisted for admin and pratos, so the flags page has a row.
  • scripts/flag.sh
    just flag list | on | off | user | pct against local D1, or remote with GH_REMOTE=1.
