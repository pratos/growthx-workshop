The agent's failures, as expect tests

cp-08 · 2026-10-28 · final · pratos with Claude Code · 2 min read · built from docs/plans/stages/cp-08-agent-failures.plan.json

When the model keeps failing, the agent's Run should end as a fact everyone can read, not hang. This stage adds FailRun and RunFailed, fails a Run with the reason after three tries, and tells it as stories: the domain, the agent loop, pi-durable after a restart.

Where we are

cp-07 has the restyled plan page and sessions panel, and just agent-serve answering through pi-durable. When the model throws, the Run stays running: the loop retries it every 1.5 s forever, the queue behind it waits, and nobody in the Session is told.

  • Only whoever started a Run can finish it (packages/domain/src/session/decider.ts); failing follows the same rule, so a person cannot fail the agent's Run.
  • The runs projection already has a result column; a failed Run keeps its reason there, so the panel needs no new field.
  • packages/agent/src/loop.ts takes the API and the brain as arguments, so tests drive it with the real session model and engine.
  • The faux model counts its calls (fauxCallCount in model.ts): that is how a test proves a restart made no second call.
  • apps/api/src/plan-room.ts lists the session commands it accepts; FailRun must join that list.

Where we end up

A Run the model cannot answer in three tries ends in RunFailed with the reason, and the next question is answered. Three stories read aloud like what happened, just test is green, and the panel shows the failed bubble.

Not doing

Out of scope for this plan, each with the reason in the same line.

  • Retrying a failed Run; a person asks again, which queues a new one.
  • Backoff between tries; three quick tries, then the reason.
  • Failing a Run someone else started; only its starter can.
  • Alerts outside the plan room.

Approach

Domain first: the event is the contract the projection, the loop and the panel read. Then the loop and its stories. The bubble last, once a failed Run exists to show.

Decisions

Each real choice in this plan, with the options compared side by side. A decided one is locked on its choice; open “Compare the options” to see why.

What happens when the model keeps failing?

Chosen: Fail it after three tries · pratos · 2026-10-28

A failed Run is a fact with a reason: everyone in the Session sees why, and the queue moves on. Retrying forever blocks the queue; dropping it records an answer that never came.
