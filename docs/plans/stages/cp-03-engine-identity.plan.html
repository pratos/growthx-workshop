Event-sourcing engine, sign-up and sign-in

cp-03 · 2026-10-28 · final · pratos with Claude Code · 4 min read · built from docs/plans/stages/cp-03-engine-identity.plan.json

People can sign up, sign in and sign out, and each of those is an event in the engine every later context will use. The engine stays small: optimistic appends, projections in the same transaction, one Sql port over four databases, and stories as tests.

Where we are

cp-02 has the words and the design: docs/DOMAIN-VOCABULARY.md with Identity's Account and Sign-in, packages/schema, the vocabulary check, the plan room map and the event design. There is no engine, no domain package and no table yet.

  • The Workers runtime caps PBKDF2 at 100,000 iterations; Web Crypto runs the same hashing in the Worker, in bun tests and in just user-add.
  • D1 has no interactive transactions, but a batch is atomic, which is all an append with its projection rows needs.
  • One stream per email (account-<email>), so two sign-ups racing for one email meet at the stream's version and the second is refused.
  • An unknown email is verified against a decoy hash, so it takes as long as a wrong password and gets the same answer.
  • D1 tables come from migrations, not setup(); a test checks that 0002_accounts.sql holds exactly the DDL the engine and projection declare.

Where we end up

Sign up at localhost:3000/signup and land signed in, your name in the header. sign-up.snap.txt reads as a story. A 21st sign-in in a minute from one address gets 429. just agent-ready reports one gap, the admin API, which cp-04 adds.

Not doing

Out of scope for this plan, each with the reason in the same line.

  • An admin API or page; it arrives with the flags in cp-04.
  • Password reset, email confirmation or OAuth; the workshop needs none of them.
  • The Thread and Session deciders; the engine is ready for them, later stages add them.
  • Rate limiting sign-in; Cloudflare's rate-limiting rules can do it outside this code.

Approach

Engine first, with its own tests, because every context will run on it. Then the account context as stories. Then the HTTP edge, seeds and pages, which only map onto it.

Decisions

Each real choice in this plan, with the options compared side by side. A decided one is locked on its choice; open “Compare the options” to see why.

Chosen: Our own, Rails 8 style · pratos · 2026-10-28

Two tables and one hash function are small enough to read in one sitting. Ours runs on the engine like every other context, so a sign-up is an event with a story.

Phase 1 Engine: event store, one Sql port, stories

not started · 0/4

packages/engine appends against an expected version, writes projections in the same transaction, and runs unchanged on bun:sqlite, a Durable Object, D1 and Postgres.

Changes

Each file this phase touches and what must be true of it afterwards. Code appears only as a contract other code depends on.

  • packages/engine/src/kernel.ts
    Messages, deciders, defineCommand and defineEvent, rejections, and the given-when-then expect harness.
  • packages/engine/src/sql.ts
    The one port every database implements; a unique-key violation becomes a WriteConflict.
  • packages/engine/src/store.ts
    One stream_events table, keyed by stream and version; execute retries a conflict three times.
  • packages/engine/src/adapters/
    bunSqlite, durableObject, d1 (one atomic batch) and postgres layers for the Sql port.
  • packages/engine/src/story.ts
    story(layer, dir) runs steps on real SQL; each then lists exactly what that step appended.
  • packages/engine/test/store.test.ts
    On bun:sqlite and PGlite: same-write projections, stale appends conflict, failed projections roll back.

Phase 2 Account context: sign up, sign in, sign out

not started · 0/3

The account decider turns the four commands into AccountOpened, SignedIn and SignedOut. Both stories pass and read as prose.

Changes

Each file this phase touches and what must be true of it afterwards. Code appears only as a contract other code depends on.

  • packages/domain/src/account/decider.ts
    Hashing happens before decide; the decider sees a hash and whether it matched.
  • packages/domain/src/account/password.ts
    PBKDF2-SHA256 with Web Crypto and a constant-time compare; tokens stored only as SHA-256.
  • packages/domain/src/account/view.ts
    accountsView: the two tables, written in the same transaction as each event.
  • packages/domain/src/account/accounts.ts
    The Accounts service: decode, hash, execute on the account's stream, read the projection.
  • packages/domain/src/account/account.expect.test.ts
    Two stories through the real engine on in-memory bun:sqlite, with a fixed clock.
  • packages/domain/src/account/__expect__/sign-up.snap.txt
    The sign-up story, every hash printed as •••.
  • packages/domain/src/account/__expect__/sign-in.snap.txt
    Wrong password and unknown email read alike; a second sign-out records nothing.

Phase 3 HTTP, seeds and pages: sign up in the browser

not started · 0/6

The API serves /auth/* by bearer token or HttpOnly cookie; local D1 is migrated and seeded through the engine; the web app signs people in.

Changes

Each file this phase touches and what must be true of it afterwards. Code appears only as a contract other code depends on.

  • apps/api/migrations/0002_accounts.sql
    stream_events, accounts and sign_ins, with the exact DDL the engine and projection declare.
  • apps/api/test/migrations.test.ts
    Fails when the migration and the code's DDL drift apart.
  • apps/api/src/auth.ts
    HTTP onto Accounts; sign-up and sign-in limited to 20 a minute per IP.
  • apps/api/src/index.ts
    Mount /auth; /readyz reports the account count, or that 0002 is not applied.
  • packages/db/seed.ts
    Opens admin, Sam and the agent through the real engine; prints the rows as SQL.
  • .dev.vars.example
    Local-only ADMIN_, USER_ and AGENT_ emails and passwords, read by the seed.
  • scripts/user-add.sh
    Asks for the password without echoing it, records AccountOpened; GH_REMOTE=1 for prod.
  • justfile
    Adds seed and user-add; up and reset now seed; test covers engine, domain and api.
  • apps/web/src/lib/session.ts
    Server functions for sign-up, sign-in, sign-out and the current account; cookie on the web origin.
  • apps/web/src/routes/signup.tsx
    Name, email and password; on success, signs in and goes home.
  • apps/web/src/routes/login.tsx
    Email and password; a refusal shows as a sentence, the fields keep their text.
  • apps/web/src/components/Header.tsx
    Your name and Sign out, or Sign in and Sign up; rechecks on navigation.
  • apps/api/wrangler.jsonc
    ratelimits: AUTH_LIMIT and WRITE_LIMIT, top level and env.demo; account_id pinned.
