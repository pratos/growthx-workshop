Resolve a comment thread into a decision

GH-12 · 2026-10-28 · implementing · pratos with Claude Code · 2 min read · built from docs/plans/2026-10-28-resolve-thread.plan.json

Today a comment thread on a block just ends. After this plan, a person or the agent resolves it with one sentence of what was decided, and that decision stays attached to the block with who decided and when. It ships behind the resolve-thread flag, off by default.

Where we are

Threads can be opened and replied to. Nothing records how a thread ended, so the same question gets argued again a week later. The plan room already keeps every change as an event, so a decision can be one more fact in that log.

  • The plan room appends every event a command produces in one synchronous block, so two events from one command land together or not at all.
  • Flags are read once per request and passed to the plan room as names; a function would arrive as a promise and read as true.
  • The domain vocabulary already names Decision and bans resolution, verdict and outcome.

Where we end up

Resolving a thread records two facts, ThreadResolved and DecisionRecorded. A second resolve is refused. The plan page shows the decision on the thread, and every open tab sees it at once. People without the flag see the thread as before.

Not doing

  • Reopening a resolved thread; nobody has asked for it yet.
  • Editing a recorded decision; a change of mind is a new thread.
  • Notifications outside the plan page.

Approach

Domain first, because event shapes are the contract everything else reads. Then the flag and API, so the behaviour exists and is off. Then the page, with every state shown first.

Decisions

When someone resolves a comment, do we save one record or two?

Chosen: Two records · pratos · 2026-10-27

Two records keep "the comment is closed" and "this was decided" apart, so the decision log can count decisions on its own. Both were built and their tests passed.

Phase 1 Domain: resolve records two facts

done · 3/3

The thread decider accepts ResolveThread and returns ThreadResolved then DecisionRecorded. Resolving twice is refused by the state type, not by a check.

Changes

  • docs/DOMAIN-VOCABULARY.md
    Add ResolveThread and DecisionRecorded under Thread and Decision, before any code names them.
  • packages/domain/src/thread/decider.ts
    Add the command, the two events, and the resolve case in decide.
    ResolveThread    = defineCommand('ResolveThread', { threadId, by, decision })
ThreadResolved   = defineEvent('ThreadResolved',  { threadId, by })
DecisionRecorded = defineEvent('DecisionRecorded', { threadId, blockId, by, decision })

type ThreadState = { kind: 'none' } | { kind: 'open'; blockId: string } | { kind: 'resolved' }
  • packages/domain/src/thread/thread.expect.test.ts
    One expect test for resolve, one for resolving twice, one for the flag being off.
